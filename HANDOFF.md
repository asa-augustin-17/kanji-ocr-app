## Architecture decisions worth knowing before touching code

**Project setup.** `KanjiScanner/project.yml` is the source of truth (XcodeGen). Never hand-edit `.xcodeproj` — run `xcodegen generate` after changing `project.yml` or adding/removing source files it doesn't glob automatically. GRDB.swift (SPM) is the SQLite layer.

**Dictionary data.** `data-pipeline/build_dictionary.py` builds `kanji_scanner.sqlite` from three sources: KANJIDIC2 + JMdict XML (EDRDG, CC BY-SA), plus [JmdictFurigana](https://github.com/Doublevil/JmdictFurigana) (CC BY-SA) for per-character furigana. Raw sources are gitignored (re-downloadable — see README for URLs); the compiled sqlite *is* committed (via LFS) since the app needs it to build. Schema: `kanji` (character, onyomi/kunyomi/meanings as JSON, stroke_count, grade, jlpt_level, frequency_rank, radical), `words` (surface_form, reading, meanings JSON, part_of_speech, is_common, `furigana_segments` JSON), joined to kanji via `word_kanji_map`. `words` now also imports **kana-only entries** (both katakana and, imminently if US-32/35 land, hiragana), not just kanji-containing ones — `surface_form == reading` for these. Indexes exist on `kanji.character`, `words.surface_form`, and `words.reading` (the last needed for the kanji-fallback lookup below). No `wanikani_level`/`is_joyo` columns yet (parked gap #2).

**Segmentation (`Segmenter.swift`) — now four matching strategies, one per character class, all in `segment()`'s main loop:**
- **Kanji**: longest-match-first against `words.surface_form`. A run of consecutive kanji that all fail compound-matching gets grouped into one token (not fragmented) so the UI can show a "no compound match" state. If that run turns out to be exactly one character, it *also* gets checked against `words.surface_form` directly (US-19) — many single kanji (目, 手, 心) are standalone words in their own right.
- **Katakana**: same longest-match-first, but tries an exact surface-form match first, then falls back to matching by *reading* against a word with a distinct kanji surface form (US-23's kanji-fallback — コーヒー → 珈琲). An unmatched run becomes one tappable "no entry" region *unless* it's a single character (US-33) or entirely punctuation connectors ・/ー (BUG-012) — both of those produce no token at all, since OCR occasionally misreads a non-Japanese symbol as a lone katakana character or a period as ・.
- **Arabic digits**: a digit run followed by a kanji counter (josūshi) converts to its kanji-numeral equivalent (0-10 only — real dictionary coverage is concentrated there) and looks that up (US-31, e.g. "1匹" → 一匹). No fallback token on a miss — ordinary numbers (prices, page numbers) shouldn't become dead tap targets.
- **Hiragana**: not yet implemented (US-32/35) — plan is a length-≥3 floor with *no* POS filtering (an early plan to exclude "purely grammatical" entries was wrong — real examples like だけど, なのに, たりとも are genuine, lookup-worthy grammar, not noise; the length floor alone does the useful filtering, since risky short fragments are concentrated at length 1-2).

Two patterns established this session worth reusing: (1) when a token's literal printed text differs from what actually matched (kanji-fallback, numeral conversion), the `SegmentToken.range` covers the text as printed, but `result.word`/`kanjiBreakdown` come from the richer matched entry. (2) For character classes prone to OCR noise or ambiguity (digits, single katakana), don't build a grouped "unmatched" fallback token the way kanji/katakana runs do — just skip and advance, no dead tap target.

**Camera capture pipeline** (`CameraViewModel.swift`) — unchanged this session, still guarded against BUG-001/003/004/005 (single reused `AVCaptureVideoPreviewLayer`, capture cropped to preview's visible rect, manual pixel rotation since `cgImageRepresentation()` ignores `videoRotationAngle`, `connection.isActive` guard before capture).

**Scan overlay zoom/pan** (`ScanOverlayView.swift`) — unchanged this session. Touch-anchored pinch zoom with a hard clamp on `offset` (BUG-010's kink is a known, accepted-for-now limitation — see BUGS.md). Tap-vs-pan disambiguation via an `isInteracting` flag gating a region `Button`'s tap action, not custom hit-testing (BUG-008/009's lesson). **Do not re-attempt a `Grid`-based or `Color.clear`-cell-based fix for alignment bugs** without re-reading BUGS.md first (BUG-011's saga) — a hardcoded `.padding(.leading, N)` is what actually worked.

**Results display** (`ResultsView.swift`): `WordSection` renders for any `word != nil` result regardless of kanji-breakdown length (so US-19's single-kanji-as-word case needed zero UI changes); falls back to `KanjiDetailView` (plain kanji) or `NoMatchView` (no entry) otherwise. Furigana rendering has two paths — `SegmentedFuriganaText` (per-character, when `furigana_segments` data exists) and `WholeWordFuriganaText` (fallback) — both skipped entirely when `surfaceForm == reading` (every katakana-only word), since ruby text identical to the headword is just noise.

## Working conventions established this/last session

- **Never commit until the user has explicitly confirmed a UI/behavior change on-device.** Build + unit tests passing is necessary but not sufficient. This session, "confirmed" mostly happened via the user testing on their physical device after I verified end-to-end in the Simulator first.
- **Verify every `Segmenter`/dictionary change against the *real* bundled dictionary before considering it done, not just the small seeded test DB.** Pattern used all session: temporarily override `RootView.swift`'s initial `screen` state to a `.results` case built directly from `Segmenter.segment(...)`/`DictionaryDatabase.shared`, build, screenshot via the Simulator, then `git checkout -- RootView.swift` to revert before finalizing. Never leave this debug harness in a commit.
- **`xcodebuild build`/`test` can silently skip recompiling changed Swift files in this environment** (confirmed by direct investigation — a build reported success while the compiled binary provably lacked a just-added string literal). **Always use `clean build`/`clean test`** when verifying a Segmenter/model change; a plain incremental build is not trustworthy here.
- **Use the in-app Simulator panel** (`mcp__Claude_Code_iOS_Simulator__control` `attach`/`screenshot`), not the standalone Simulator.app — the user explicitly asked for this. Note the panel is backed by the same underlying process as Simulator.app, so quitting Simulator.app manually tears down the booted device too; let `attach`/`launch` manage it.
- Commit messages reference the relevant `BUG-XXX`/`US-XXX` ID(s); BUGS.md/STORIES.md get updated in the **same commit** as the code change, never a separate one.
- When reverting a change, prefer `git checkout <commit> -- <path>` over manually re-editing files back to a prior state.
- New feature requests get logged as user stories (STORIES.md) whether or not they're implemented immediately; defects get logged in BUGS.md. Backlog stories leave `Version` empty (`—`) until a version is actually assigned — either pre-assigned during planning before development starts, or set once the story ships, at which point it moves out of the Backlog table into its own version section.
- STORIES.md status vocabulary is deliberately just three values — **Not Started / Implemented / Closed** — no separate "Verified" or "superseded" status; that nuance goes in the story's own prose instead. This was a deliberate simplification after an earlier attempt at a fourth status caused real confusion.
- **Research before implementing, especially before excluding data on a heuristic.** More than once this session, a first-pass filtering idea (POS-based exclusion for hiragana, "always show a no-entry box for single unmatched characters") turned out wrong once actual data or a real motivating example was checked directly — pull the real numbers/examples before committing to a filter, not just reasoning about plausible-sounding categories.
