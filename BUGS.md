# Bug Log

Tracks bugs found during development/testing, how they were fixed, and where. Rows are sorted by ID, ascending.

## Status values
- **Open** — reported, not yet investigated/fixed
- **In Progress** — actively being worked
- **Fixed** — fix implemented and verified (simulator and/or device)
- **Reverted** — a fix was attempted and shipped, but caused a worse regression and was rolled back; the original bug is unfixed again
- **Deferred** — investigated, one or more fix attempts tried and rejected, but consciously set aside for now rather than continuing to iterate; not currently being worked

| <a id="bug-010"></a>BUG-010 | [US-9](STORIES.md#us-9), [US-14](STORIES.md#us-14) | On the scan overlay, zooming out while zoomed in and panned toward an edge feels like the image first zooms toward that edge, "bounces" off it, then slides toward center — instead of one smooth motion. Root cause (confirmed via derivation): a hard `min`/`max` clamp on the pan offset is mathematically guaranteed to produce a kink (a sudden change in the *rate* of motion, though position itself never jumps) at the exact instant it starts constraining a continuously-changing value — true regardless of how the pre-clamp value is computed. Two fix attempts, both reverted: (1) removing the mid-gesture clamp entirely and only correcting at gesture end reintroduced [BUG-007](#bug-007) (visible overscroll during the live gesture). (2) A full rewrite to a "visible rect" model (tracking which crop of the image is shown, constrained to bounds every frame — the same approach UIScrollView-based zoom uses); the kink persisted regardless, and per the user's own on-device assessment this rewrite wasn't judged to be an improvement over the original implementation overall — the original's `clampedOffset` already prevented overscroll too, just via different math, so the rewrite wasn't the clear win it was initially framed as. Layering a `tanh`-based smooth clamp on top of the rewrite eliminated the kink but introduced noticeable pan "stickiness" well before the true edge (tanh compresses movement significantly before saturating, not just very close to it), and was also rejected. **Decision:** deferred. Reverted all the way back to the last-known-good commit (`44583ec`, [BUG-008](#bug-008)'s fix) — both on the merits (the rewrite wasn't judged better) and because it was never itself committed, so manually reconstructing it risked subtle unverified differences. The kink is a known, accepted-for-now limitation of the current implementation. Revisit with a fresh approach if prioritized later. | Deferred | 2026-08-23 | — | v1 |

The flag clears ~150ms after the gesture ends (not synchronously) to avoid a race with a button's own tap resolving at the same touch-up moment.
