# Bug Log

Tracks bugs found during development/testing, how they were fixed, and where. New entries go at the top of the table.

| ID | Description | Status | Date Detected | Date Fixed | Version |
|----|---|---|---|---|---|
| BUG-009 | Follow-on effect of BUG-008's fix — see that entry. Two rounds of attempted fixes (smallest-region-wins hit resolution, then hit-testing the touch-down point instead of the release point) improved but did not fully resolve it; taps remained unreliable overall. Rather than continue iterating, BUG-008's whole approach was reverted (see BUG-008). | **Reverted** | 2026-08-22 | — | v1 |
| BUG-008 | Starting a pan or pinch-to-zoom gesture with a finger positioned over a bounding box would sometimes unintentionally open that region's results screen. Root cause: each region used a SwiftUI `Button` for tap-to-select, and `Button`'s built-in tap recognizer tolerates a fair amount of finger movement before it stops counting as a tap — enough to fire even when the user was clearly starting to pan/zoom, not tap. **Attempted fix:** replaced the per-region `Button`s with a single `DragGesture(minimumDistance: 0)` doing manual movement-threshold-based tap/pan disambiguation and hit-testing. This introduced BUG-009 (most boxes became unresponsive) and, even after two follow-up patches, taps stayed unreliable — net worse than the original problem. **Reverted in full** back to the per-region-`Button` approach on 2026-08-22; the original accidental-tap-during-pan issue is back and unfixed, but tap responsiveness is restored. Needs a fresh approach if revisited. | **Reverted** | 2026-08-22 | — | v1 |
| BUG-007 | After zooming in on the scan overlay, it was possible to pan the image past its edges, revealing empty black space behind it — the pan offset was never bounded to the image's actual extent. Fixed by clamping `offset` on every pinch/pan update to the maximum the current zoom level allows (`contentSize * (scale - 1) / 2` in each direction), so the zoomed image always fully covers the viewport. | Fixed | 2026-08-22 | 2026-08-22 | v1 |
| BUG-006 | On the scan overlay's pinch-to-zoom, a second (or later) pinch gesture caused a visible jump right as the touch began, before any actual zoom change. Root cause: zoom was implemented via `.scaleEffect(scale, anchor:)`, moving `anchor` to the new pinch's start point each time a gesture began — since the image was already scaled from a prior pinch, snapping the anchor to a new point instantly repositions the whole image. Fixed by keeping `anchor` fixed at `.center` permanently and instead computing `offset` directly from the touch point, current scale, and target scale, so the touch location stays visually fixed continuously (zero movement at magnification = 1.0, i.e. gesture start) rather than jumping. | Fixed | 2026-08-22 | 2026-08-22 | v1 |
| BUG-005 | Tapping "Retake" (from the scan overlay) or "Scan Again" (from results) took ~5 seconds to return to the live camera view. Root cause: a brand-new `AVCaptureVideoPreviewLayer` was created and attached to the already-running `AVCaptureSession` every time the camera screen reappeared, forcing AVFoundation to renegotiate the session's connections. Fixed by having `CameraViewModel` own a single preview layer created once and re-parented into each new view instead of recreated. | Fixed | 2026-08-22 | 2026-08-22 | v1 |
| BUG-004 | Captured photo was rotated relative to how it was framed (first reported as coming out horizontal/landscape; after a first fix attempt, still off by 90° counterclockwise). Root cause: `AVCapturePhoto.cgImageRepresentation()` always returns the raw sensor-orientation pixel buffer — setting `videoRotationAngle` on the capture connection only changes the orientation *tag* in the photo's metadata, not the actual pixels. Fixed by reading the true `CGImagePropertyOrientation` from the photo's metadata after capture and baking that rotation into the pixels directly (`UIImage` + `UIGraphicsImageRenderer`). Took two fix attempts — the first (connection rotation angle via `AVCaptureDevice.RotationCoordinator`) corrected the live preview and the viewfinder-crop math (BUG-003) but not the captured pixels themselves. | Fixed | 2026-08-22 | 2026-08-22 | v1 |
| BUG-003 | Captured photo covered a much larger field of view than what was visible in the live camera viewfinder (`AVCapturePhotoOutput` captures the sensor's full frame, wider than what `.resizeAspectFill` displays on screen), so OCR was processing area the user never framed. Fixed by cropping the capture to the preview layer's actual visible rect via `metadataOutputRectConverted`. | Fixed | 2026-08-22 | 2026-08-22 | v1 |
| BUG-002 | No way to return from the Results screen to the previously captured photo to pick a different detected word/kanji region — the only exit was "Scan Again," which discarded the photo and forced a brand-new capture. Fixed by adding a "Back" action that returns to the same captured photo and its detected regions, carrying that state through the results screen instead of discarding it. | Fixed | 2026-08-22 | 2026-08-22 | v1 |
| BUG-001 | App crashed on capture when `AVCapturePhotoOutput` had no active video connection (e.g. no camera hardware present, as in the iOS Simulator) — `capturePhoto` raises an uncatchable Objective-C exception in that state instead of a Swift-catchable error, killing the process. Found during initial Simulator verification. Fixed by guarding on `connection.isActive` before calling `capturePhoto` and surfacing a normal "Couldn't capture photo" alert instead. | Fixed | 2026-08-22 | 2026-08-22 | v1 |

## Status values
- **Open** — reported, not yet investigated/fixed
- **In Progress** — actively being worked
- **Fixed** — fix implemented and verified (simulator and/or device)
- **Reverted** — a fix was attempted and shipped, but caused a worse regression and was rolled back; the original bug is unfixed again
